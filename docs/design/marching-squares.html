Marching Squares, Tile by Tile

How a grid of samples becomes contour lines, how this library implements it, and what changes once the grid is cut into map tiles.

Cell: 2 × 2 samplesCases: 16Saddle rules: 4Module: github.com/valri11/contourmap
§1

The question each cell answers

A DEM tile is a regular grid of heights. A contour at height z is the curve where the surface crosses z. We never see the surface itself, only samples at grid nodes, so the job is to guess where the curve passes between them.

Marching squares treats every 2 × 2 block of neighbouring samples as one cell and answers two questions for it: which corners are above z, and where along each edge does the crossing sit. A tile with 256 × 256 samples has 255 × 255 cells. Each one is handled independently, which is why the algorithm is simple and fast.

§2

Classify, look up, interpolate

Classify. Each corner gets one bit: 1 if the sample is above z, 0 otherwise. contourmap packs them as ul=1, ur=2, ll=4, lr=8, giving a case number 0–15. Cases 0 and 15 have no crossing and are skipped, and on real terrain that is most cells.

Look up. The case number says which edges the line enters and leaves through. An edge is crossed exactly when its two endpoints disagree.

Interpolate. Along a crossed edge with endpoint heights a and b, the crossing sits at fraction t = (z − a) / (b − a). Without this step every crossing lands on an edge midpoint and the lines come out jagged. Switch it off below to compare.

§3

All sixteen cases

Bits are written lr ll ur ul, so case 6 = 0110 means upper-right and lower-left are high. Fourteen cases have one obvious segment. Cases 6 and 9 have two high corners on a diagonal and two valid answers, drawn solid and dashed.

§3a

Saddles: the one real decision

In a saddle cell the four samples cannot tell you whether the two high corners join through the middle (one ridge) or stay apart (two hills). Upstream contourmap hard-coded an answer, const connectHigh = false, so high corners never join inside a cell. That is consistent, and consistency is what keeps polylines from breaking, but it is sometimes topologically wrong. This library keeps it as the default (SaddleConnectLow) and lets you pick another rule.

Two common fixes. The centre average samples the mean of the four corners. The asymptotic decider evaluates the bilinear surface at its saddle point, (ul·lr − ur·ll) / (ul + lr − ur − ll), which is exact for that surface. The shaded background below is the true bilinear surface above z; see which rule agrees with it as you move the level.

m := contourmap.FromFloat64s(w, h, grid)
m.Saddle = contourmap.SaddleAsymptotic   // or SaddleCenter, SaddleConnectHigh

For 20 m contours on real DTM this rarely matters visually. It matters more for 1 m intervals on flat, noisy ground, where saddles appear in clusters and the fixed rule can split one contour into many tiny loops.

§4

From segments to polylines

Per-cell segments are useless for rendering and labelling; you want long polylines. A naive approach collects segments and joins matching endpoints with a float-keyed lookup. Upstream contourmap does something neater. Because each cell's segment has a direction (high side always on the same hand), every crossed edge is the entry of exactly one segment. Two maps capture the whole graph:

// for each segment in a cell: the edge it starts on → the crossing point,
// and that point → the edge it exits through (= next cell's entry edge)
edgePoint[te] = t
nextEdge[t]   = le

Edges are keyed by integer grid coordinates, so neighbouring cells agree on the key for a shared edge without any float comparison. Stitching is then a walk:

for len(edgePoint) > 0 {
    e := /* any unused edge; prefer one on the grid boundary */
    p := edgePoint[e]; contour = append(contour, p); e = nextEdge[p]
    for {
        p, ok := edgePoint[e]
        if !ok { break }            // ran off the grid: open contour
        contour = append(contour, p)
        delete(edgePoint, e)
        e = nextEdge[p]                 // back at start: closed, c[0] == c[n-1]
    }
}

Starting from boundary edges first guarantees open contours are walked from their true start, never from the middle. Everything left after that must be a closed loop.

What this library changes

  • Arrays instead of maps. Every edge gets an integer id: horizontal edges are y·(w−1)+x, vertical edges follow them. The walk uses three flat slices (next, pts, hasIn) indexed by edge id. They come from a sync.Pool and are left clean after each call, so a whole contour map reuses the same memory.
  • Starts found by in-degree. An open contour starts on an entry edge that no segment exits through. That is either the grid border or the border of a no-data region. No boundary flag is needed, and holes work the same way as borders. Everything left afterwards is a loop.
  • Open contours keep their last point. Upstream stored crossing points only for entry edges, so every open contour lost its final segment at the border. Exit points are now stored too.
  • Deterministic output. Starts are taken in scan order, so the same input always gives the same contours, in the same order, from the same start points.
  • Block skipping. Cells are grouped into 16 × 16 blocks with a precomputed min and max. A block whose range doesn't span the level is skipped without classifying any of its cells.

On a 262 × 262 grid contoured every 10 m (41 levels), this goes from 9.7 ms, 12.8 MB and 2,459 allocations per run of all levels to 1.36 ms, 0.58 MB and 97 allocations. Most of what remains is the output itself.

§5

Many levels, edges and holes

A contour map is the single-level algorithm run once per level. Pick levels as integer multiples of the interval: k·interval for k from ⌈min/interval⌉ to ⌊max/interval⌋. Index the loop by k rather than adding the interval to a float each step, or a 0.3048 ft conversion drifts by the 40th level.

Two library details shape the result:

  • Strict comparison. A sample is “high” only if v > z. Terrain often holds exact integers, so a sample equal to the level would sit on the line and make degenerate zero-length segments. Callers usually nudge the level by a small epsilon (z − 0.0001) to avoid that.
  • No-data. The library has one internal sentinel, closed = −MaxFloat64, used by Closed() to pad the border so every contour becomes a ring. NaN means no data: cells touching a NaN emit nothing and contours stop at the edge of the hole. Convert sentinels such as −9999 to NaN before building the map. Upstream had no concept of holes, so NaN corners counted as “low” and produced NaN points.
§6

Cutting the map into tiles

A map client asks for contours one web tile at a time. If each tile is contoured on its own 256 samples, the cells that straddle tile borders are never processed: tile A's last sample and tile B's first sample are neighbours, but no single tile contains both. Every line breaks at every seam.

The fix is a halo: contour a window slightly larger than the tile using pixels from neighbours, then clip. One pixel closes the gap. Drag the halo to zero below to see the seams open.

Doing it with this library

// window: the tile plus halo pixels from each neighbour, row-major
m := contourmap.FromFloat64s(256+2*halo, 256+2*halo, window)
for _, lines := range m.ContourLevels(levels) {
    for _, c := range lines {
        for _, p := range c {
            px, py := p.X-halo, p.Y-halo   // back to tile pixel coordinates
        }
    }
}

Clip the result to the tile, plus any vector-tile buffer. Lines inside the halo duplicate the neighbour tile's lines.

Fill missing neighbours and voids with NaN, not 0. A 0 creates a cliff, and every level between the terrain and 0 then runs along the edge of the data: stacked lines that aren't terrain, plus extra work for every one of them.
